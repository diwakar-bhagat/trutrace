# Gold label review protocol

Adopted by Diwakar Bhagat, 27 November 2026.

The benchmark is only as trustworthy as its gold labels. The current
labels were drafted by an AI coding agent; they are useful for
bootstrapping the dataset, but they cannot independently validate the
system whose behaviour they were drafted alongside. Scores measured
against them are agreement with another model's labels, not
correctness. This protocol turns label review into a formal
evaluation process so that a later gold version can carry that
weight.

## The versions

- **gold-v1-ai-drafted** — the frozen labels in `datasets/`
  (`golden_dataset.jsonl` plus the campaign slice), frozen
  27 November 2026. Pending human review. Every score reported so far
  is measured against this version.
- **gold-v2-human-reviewed** — the output of a human review with
  the tool below, submitted to the workbench backend
  (`POST /api/gold/review`), which stores it as the current human
  gold. It never edits v1. Partial submissions count: the current
  gold is the newest submission, and metrics against it cover only
  the fields the reviewer actually decided.

Every benchmark run record names the gold version it was scored
against (`gold_labels_version` in workbench run records, and the
header of every `evals/gold_metrics.py` report). The PostgreSQL
`eval_datasets` rows additionally carry the dataset content hash and
`labels_status`, the provenance line that travels with the data.

**Known gap:** run records written before 27 November 2026 carry
`labels_status` (the provenance prose) but no `gold_labels_version`
identifier. They were all scored against gold-v1-ai-drafted — no other
version existed — but the field itself is absent from those files,
and historical run files are not rewritten to add it. The identifier
is present on every run recorded from the change onward.

## Freeze discipline

- The original transcripts, model outputs and AI drafted labels are
  preserved as frozen. Nothing is silently overwritten.
- Human review produces a new dataset version. A disagreement with
  the AI draft is recorded in the new version, never patched into the
  old one.
- If the underlying dataset content ever changes, the dataset version
  bumps (see `DATASET_VERSION` in `workbench/pg_store.py`) and the
  new content registers as a new version alongside the old.

## Field level review

Review is per field, not per call. For each of the 224 fields (32
calls × 7 requested fields) the reviewer independently inspects the
extracted field against the source transcript and records:

- **A ground truth status**, one of four:
  - **supported** — the transcript establishes the field as stated.
  - **uncertain** — the evidence is hedged or ambiguous; it does not
    settle the field. Uncertain is its own category, kept separate in
    every metric. It is never collapsed into supported or unsupported
    to make a binary score.
  - **unsupported** — no adequate evidence for the field exists in
    the transcript.
  - **contradictory** — the transcript contradicts the field.
- **The evidence**: the exact supporting span, marked in the
  transcript, or an explicit record that no adequate evidence exists
  (span cleared). The span the reviewer saw from the AI draft is
  accepted only by the reviewer leaving it in place; adjusting or
  clearing it is a first class action, and the export says which
  happened (`evidence_source`: `reviewer`, `ai_draft`, or `none`).
- **An adjudication note** for ambiguous cases: what made the case
  hard and how it was resolved. Ambiguity is recorded, not forced
  into a binary answer.

## The tool

`tools/gold_review.html` (generated by `tools/build_gold_review.py`,
served on Cloudflare Pages at /review and openable as a local file)
walks the reviewer through all 224 fields: transcript with the AI
drafted evidence span highlighted, the field and its AI drafted
status, controls to set the ground truth status, adjust or clear the
span by selecting transcript text, and add an adjudication note.
Progress is visible across the whole set and per split.

In-progress state persists in the page's localStorage as a working
draft. **The primary path is submission**: the page's "Submit review
to backend" action posts the review to `POST /api/gold/review`, and
the backend stores it (PostgreSQL `eval_gold_submissions`, one row
per submission, or `gold/gold_labels_v2.json` in the file store) as
the current gold-v2-human-reviewed and reports back the coverage it
recorded. The page shows that confirmation, including the recorded
field count. Exporting `gold_labels_v2.json` — which carries the
dataset version identifier, per call and field the human status,
the evidence span text and offsets, the adjudication note, the
reviewer name and the export timestamp — remains as a fallback for
when the backend cannot be reached; an export can also be submitted
later by importing it back into the page, or scored directly with
the CLI harness. Submitting again replaces the current gold with
the newest submission; earlier submissions stay on record in the
database.

## Metrics against a gold version

`evals/gold_metrics.py` scores recorded runs (no model calls) against
a named gold version: precision, recall, false positive rate and
false negative rate on verification decisions, evidence accuracy
(whether cited spans match gold spans), and abstention quality for
gold uncertain and gold unconfirmed fields, measured separately and
never folded into the positive or negative classes. Its header states
which gold version it scored against; against gold-v1-ai-drafted it
states plainly that the numbers measure agreement with AI drafted
labels, not validated correctness.

The same computation is served at `GET /api/gold/metrics` (and the
current version and coverage at `GET /api/gold/status`), which is
what the demo page's gold tile reads. While coverage is partial, the
endpoint scores only the reviewed fields and labels the result
`reviewed_fields_only`: unreviewed fields are excluded, never scored
against the AI draft under a human label. The CLI harness with an
exported file keeps its overlay semantics (unreviewed fields keep
the AI drafted label) and says so in its header; the endpoint is
stricter because its numbers are presented as validated metrics.

## The held out rule

The held out split (12 of the 32 calls, `datasets/SPLIT.md`) is not
used to tune prompts, rules or thresholds. Tuning uses the dev 20
only; the held out 12 are opened for final evaluation runs.

Disclosure, carried from `datasets/SPLIT.md`: the split was frozen
mid build, after a first round of fixes driven by failures observed
across all 32 cases. The held out set is therefore **not clean room**,
and reports say so wherever held out numbers appear. The freeze
discipline above is what keeps it clean from here on.

## Scale, honestly

The frozen set is 32 calls (224 fields) today. The protocol's target
is 100 to 200 carefully human reviewed calls, with a second reviewer
adjudicating ambiguous cases: a small defensible set over a large AI
labelled one. That expansion is a later decision, not part of the
current build. Until the human review of the existing 224 fields is
done and submitted as gold-v2-human-reviewed, every TruTrace score
should be read as agreement with AI drafted labels.
